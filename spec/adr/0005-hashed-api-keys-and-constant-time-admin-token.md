# ADR-0005: API keys stored as SHA-256, admin token compared in constant time

* **Status:** accepted
* **Date:** 2026-10-02

## Context
Tenants authenticate every check with an API key (`X-API-Key`), the operator uses one admin bearer
token. A Redis dump, a backup or a `MONITOR` session must not reveal usable keys (threat T1), and the
admin token must not be guessable byte by byte from response timings (threat T2). Key lookups happen
on every check, so they must stay O(1).

## Options considered
1. **Store keys in clear text**: anyone who reads Redis can impersonate every tenant.
2. **bcrypt/argon2 per key**: right for passwords, but the lookup would need the tenant id first and
   costs ~50 ms of CPU per check: far over the latency budget.
3. **SHA-256 of a long random key**: keys are 128 random bits (`rg_` + 32 hex chars from a CSPRNG),
   so there is nothing to brute-force or look up in a dictionary; a fast hash is enough, and the
   hash itself is the lookup key `rg:key:<sha256>`.

## Decision
Option 3. The plain key is returned **once**, when the tenant is created or the key is rotated; the
API afterwards shows only `keyPrefix` (`rg_` + 6 hex). Rotation deletes the old hash, so the old key
stops working at once. The admin token is generated by the operator (`openssl rand -hex 32`; the
runbook says so, the code does not check the length); an unset token becomes a random one per
process (logged as a warning, so the admin API is effectively locked). It is compared with a
constant-time function. Neither the key nor the token is ever logged.

## Consequences
* A leaked Redis snapshot leaks tenant names and policies, not credentials.
* A tenant that loses its key must rotate; there is no "show my key".
* The prefix makes support possible ("is the key starting `rg_3fa9c1` the current one?") without
  exposing anything useful.
